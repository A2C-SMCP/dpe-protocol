    0.6 升级须知¶

    0.6 是 0.x 阶段的一次不兼容升级：规范文档、Python SDK（dpe-hash / dpe-sdk / dpe-conformance）与 Rust SDK（dpe-hash / dpe-sdk）一起从 0.5.0 升到 0.6.0。本页以已发布的 0.5.0（文档 v0.5.0、py-v0.5.0、rs-v0.5.0）为基线，先按读者说明要做什么，再给出逐条行为变化清单。细节见对应 Issue / PR。

    总体结论¶

    • hash 契约仍是 dpe1，所有 hash 值没有任何变化。 本周期不改 hash 算法、JCS 规范化、URI 规范化或向量期望值。已落库数据、已存的 doc_hash / page_hash / content_hash 照常有效，不需要重算，也不会引发重推或重学。
    • 线上 HTTP 协议面没有变化：没有新增或改动端点、请求/响应字段、错误码或状态码映射。0.6 改的是客户端在契约升级期如何使用前置条件、发送前如何拒收非法凭证、运行器如何归类本地构造失败，以及一致性套件扩大判红面。
    • 变化集中在五方面：契约升级期的前置条件（规范 + 两个 SDK + 运行器行为）、Python SDK 的 outcome_unknown 标记、Authorization 值的客户端字符集校验、运行器新增 request_invalid、一致性套件新增检查。
    • 依赖范围：下游按 >=0.6.0,<0.7 声明依赖（文档与两个 SDK 保持相同的 X.Y）。

    按读者处理¶

    服务端实现方¶

    • 规范面没有新增服务端义务：端点、字段、错误码与状态码映射不变；#253 只约束客户端发出的头值，#256 只改运行器本地的错误归类，服务端接收、错误码与状态码不变。
    • 若要引入新契约（服务端开始同时接受两个 hash 契约）：按 hash 契约 1 §6 的新前置约束，参考 SDK 的推送器 MUST 已支持过渡期以旧契约的同步状态值作前置条件，之后才能引入——否则冲突保护会退化为以读到的值覆盖。0.6 的两个 SDK 已具备该能力（#218-2）；仅用于测试的 dpex 演练不算引入新契约。
    • If-Match 按值所带契约比较是 http.md §3.1 的既有要求（过渡期内新旧契约的值都能匹配，与请求声明的契约无关），不是 0.6 新增；实现自检时按既有要求核对。
    • 跑分器判红面扩大：dpe-conformance==0.6.* 的 order 章新增 2 条检查（#259，见下文第 5 节）。合规服务端不受影响；先判 blob、后判前置条件的实现会被判红。需要的身份是 full，不需要钩子。
    • CI 执行数基线请按新的计数更新：全量 282 条中执行 281 条、skip 1；order 章 54 条。

    跑分器（dpe-conformance）使用者¶

    • dpe-conformance X.Y.* 校验规范文档 X.Y.*：0.6 的跑分器校验 0.6 规范，CI 里请升到 dpe-conformance==0.6.*（建议精确锁定补丁号）。
    • 配置加载阶段拒收非法 authorization（#253）：配置里的字面量值或 env 变量值不合 http.md §6 时，开跑前以退出码 2 退出，且不回显值。以前这类配置不在加载阶段拦截。
    • order 章新增 2 条检查（#259）：commit 的前置条件判定（core §3.3 第 5 步）先于 blob 可得性（第 6 步），覆盖无会话（内联页与元素）与有会话（暂存上传）两个变体。合规服务端不受影响。
    • 接入方式、身份与钩子要求不变；执行数基线与检查总数见上一节。

    运行器（dpe-run）运维方¶

    • 新增实例级错误码 request_invalid（#256）：source: runner、retryable: false、退出码 3。0.5 的临时口径是轮级 remote_unavailable（可重试、退出码 2），现已改为该专用码。详见下文第 4 节。
    • 触发范围是配置错误、不会自行恢复：remote URL 合乎 http.md §1 文法却无法构造请求（如非法 A-label 主机），或请求头字段值不合 http.md §6（含 #253 的字符集：CTL、obs-text、首尾 SP/HTAB）。修正实例配置或凭证后重跑即可，无需删除登记；此前结果未知的写入意图照常保留。
    • 运行器不在实例级预校验凭证：非法凭证会在构造首个 remote 请求（能力获取）时失败，此时未发出任何字节，同样归为 request_invalid。provider（CredentialProvider）自己抛出的异常不属于本类。
    • 运行器的「本地构造失败」归类依赖 SDK 的 LocalRequestError / ErrorKind::LocalRequest；升级 SDK 后行为随之生效。

    SDK 使用方¶

    • 契约过渡期：同步状态里的 L 是旧契约值时，两个 SDK 直接把它作 base（If-Match / move 的 base_hash），交给服务端 CAS 裁决；原来「以读到的值覆盖」的情形现在报冲突——这是可观察的行为变化，随 0.6 不兼容周期发布。详见下文第 1 节。
    • 新增公开 API：accepted_contracts()（Python ProtocolCore / Rust ProtocolCore），返回服务端声明支持且本 SDK 认识的契约；推送器用它判断旧 L 是否仍可作前置条件。expected_base 接受服务端仍支持的任何契约的值，不再只限当前声明的契约。
    • 跨契约 move：遇到 DPE_ALREADY_EXISTS 后重读源与目标，两边相等时改为删除源文档（仍用旧 L 作 If-Match）；源被改写由服务端 CAS 判冲突。
    • 两种保守退化：旧契约待定意图与 R 不可比，可能误报冲突；DELETE 收到无 problem 体 412 时，head 值与旧契约 If-Match 不可比，按冲突处理。两者都只多报冲突、不覆盖他人内容。
    • Authorization 字符集（#253）：Python 侧非 ASCII 凭证以前由 httpx 抛 UnicodeEncodeError，现在改为 LocalRequestError（确定未发出）；两侧首尾 SP/HTAB 同样在构造阶段拒绝。Rust 侧含 obs-text 或首尾 SP/HTAB 的凭证不再发出，改为 ErrorKind::LocalRequest。详见下文第 3 节。
    • Python outcome_unknown（#208-B）：写前持久化失败、收尾持久化失败与 provider 异常三处的标记值有变化。按 outcome_unknown 决定是否保留待定意图的调用方，不再需要多保留一轮。详见下文第 2 节。
    • #242a / #242b 无需动作：两个 SDK 与 Python 运行器的 hash 复用属于兼容的性能改动，公开签名与语义不变。

    只用 hash 核心的调用方¶

    • dpe-hash 的 hash 值与错误码（DPE_VALIDATION 等）不变，vectors/ 零改动；本周期没有 hash 规则变化。
    • 无动作；如需放宽依赖上限，按 >=0.6.0,<0.7 声明。

    行为变化清单¶

    1. 契约升级期：以旧契约的 L 作前置条件（#218 / PR #261、#266）¶

    同步状态与待定意图中的 doc_hash 带契约前缀。请求声明契约已切换、而同步状态里的值 L 仍是旧契约时，L 与按请求声明契约读到的 R 不可比。0.5 把这种 L 按缺失处理，退化为「以 R 为 base_hash」这一冲突保护最弱的路径；0.6 改为服务端仍接受 L 的契约时，直接以 L 作前置条件，由服务端按值所带契约比较 If-Match、以 CAS 裁决。

    规范改动：connector 契约 §7.2（判定表新增跨契约一行）、hash 契约 1 §6（引入新契约的前置约束）。两个 SDK 对等实施。

    情形（服务端仍接受 L 的契约） 0.5.0 0.6.0
    R 存在 按缺失处理：以 R 为 base_hash 写入（两轮之间他人的写入无法识别） 以 L 为 base_hash 写入，由服务端 CAS 裁决；DPE_PRECONDITION_FAILED 按冲突处理
    R 不存在 按缺失处理：commit 以 if_absent 新建 按冲突处理（视同他人删除或移走）
    R 与 L 是同一内容、不同契约 按缺失处理，以 R 为 base 以 L 为 base，CAS 按值比较命中，按已达成或正常写入处理
    move 的源侧 按缺失处理，以 R 为 base 发出 直接以 L 为 base_hash 发出
    跨契约 move 得到 DPE_ALREADY_EXISTS 按目标被占用报条目失败 重读源与目标：两者相等时改为删除源（仍用旧 L 作 If-Match，即使重读到的源值不同）；源被改写由服务端 CAS 判冲突
    服务端已不再接受 L 的契约 按缺失处理 按缺失处理（不变）

    可接受的保守退化（只多报冲突、不覆盖他人内容）：

    • 旧契约的待定意图与 R 不可比，对账时可能误报冲突（判定表第一行已达成的情形除外）。source_wins 下按常规冲突重读后再提交（仍经 CAS），report 下条目失败并如实上报。
    • DELETE 收到既无 problem 体、也无 DPE-Error-Code 头的 412 时，先 head 再判定；head 返回的是请求声明契约下的值，与 If-Match 的旧契约值不可比，无法区分中间层误判与真实冲突——文档不存在时仍按已达成，否则按冲突处置。

    写入结果与状态记录：move 在旧契约 base 下的结果按请求声明的契约校验；成功 / 已达成 / 删源迁移后，同步状态与意图日志记录的都是请求声明契约下的值；DPE_ALREADY_EXISTS 后重读源与目标两侧都失败时，两侧 SDK 都优先报目标侧错误。

    引入新契约的顺序：hash 契约 1 §6 新增前置约束——服务端开始同时接受两个契约（仅用于测试的 dpex 演练不算）之前，参考 SDK 的推送器 MUST 已支持过渡期以旧契约的 L 作前置条件，不得因请求声明的契约已切换就把旧契约值按缺失处理。0.6 的两个 SDK 已满足。

    2. Python：outcome_unknown 的三处标记修正（#208-B / PR #264）¶

    StatefulPusher / AsyncStatefulPusher 在本地持久化失败与凭证 provider 异常时，异常上的 outcome_unknown 标记按「写请求是否确定未发出」修正。异常类型与实例都不变（StateStore 的原始异常、provider 的原始异常原样抛出），只改标记值。

    场景 0.5.0 0.6.0
    写前意图持久化失败（StateStore.save 抛错） True False（写请求确定未发出）
    CredentialProvider.authorization() 自己抛错 True False（该次尝试确定未发出；此前已有结果未知的尝试时，整体仍为 True）
    写后收尾持久化失败 · 本批发过写请求 True True（无变化）
    写后收尾持久化失败 · 无写计划（含全部 unchanged） True False
    flush() 持久化失败 True False（flush 不发写）
    • provider 异常不包装成 LocalRequestError：它可能是暂时性失败，不能据此判为不可重试（与 #256 的 request_invalid 归类相区分）。
    • 调用方按 outcome_unknown 决定是否保留待定意图；上述三处都不再需要多保留一轮。Rust 侧 StateStore 错误的 outcome_unknown() 规则有对等的文档说明，行为与 Python 一致。

    3. 两个 SDK 与跑分器：Authorization 值字符集（#253 / PR #267）¶

    http.md §6 规定 Authorization 的值必须为空，或形如 VCHAR [ *( VCHAR / SP / HTAB ) VCHAR ]：不允许 obs-text（%x80-FF），也不允许首尾 SP / HTAB。客户端对其构造并发出的全部请求头字段值 MUST 按此判定，违例在请求构造阶段拒绝，按本地构造失败（「确定未发出」）处理。

    场景 0.5.0 0.6.0
    Python：凭证含非 ASCII（obs-text） httpx 抛 UnicodeEncodeError LocalRequestError（确定未发出）
    Python：凭证首尾含 SP / HTAB 不在客户端拒绝范围内 构造阶段 LocalRequestError
    Rust：凭证含 obs-text 或首尾 SP / HTAB 会发出 ErrorKind::LocalRequest（确定未发出）
    dpe-conformance：配置的 authorization 不合 §6 加载阶段不拦截 加载配置时以退出码 2 退出，不回显值
    • 规范只约束客户端构造并发出的头；底层库自动添加的 Host / User-Agent 等不在判定内。
    • 服务端接收、错误码与状态码不变。
    • 运行器侧的实际归类见第 4 节（request_invalid）。

    4. 运行器：实例级 request_invalid（#256 / PR #268）¶

    0.5 对「remote 请求在 SDK 构造阶段被拒绝」的临时口径（轮级 remote_unavailable，可重试，退出码 2）改为专用的实例级错误码。

    场景 0.5.0 0.6.0
    非法 A-label 主机（URL 合 http.md §1 文法但构造不出请求） remote_unavailable（round 级，source: remote，retryable: true，退出码 2） request_invalid（instance 级，source: runner，retryable: false，退出码 3）
    请求头值不合 http.md §6（CTL、obs-text、首尾 SP / HTAB） 同上 同上
    非法凭证字符集 同上 能力获取时构造失败 → 同上
    CredentialProvider 自己抛错 — 不属于本类，保持原归类
    • 归类依据：SDK 抛出的 LocalRequestError 类型（请求在构造阶段被确定拒绝、未发出）；不看「确定未发出」标记，并忽略结果是否未知。
    • 凭证不预校验：运行器不在实例级复现凭证字符集判定；非法凭证会在构造首个 remote 请求（能力获取）时失败，此时未发出任何字节。
    • 后续行为：写请求在此前尝试中结果未知时，写入意图照常保留；修正配置 / 凭证后重跑即可，无需删除登记。
    • 服务端行为不变（只约束客户端）。

    5. 一致性套件：commit 的前置条件判定先于 blob 可得性（#259 / PR #263）¶

    order 章新增 2 条检查（core §3.3 第 5 步先于第 6 步）：

    • 无会话变体：seed v1 后，以错误 If-Match、内联页对象与全部元素对象提交 v2；Image 元素引用的唯一 blob 不在本文档、也不在请求中。错误前置条件先得 412 + DPE_PRECONDITION_FAILED；正确前置条件才得 DPE_MISSING_CONTENT，缺失清单只含该 blob。
    • 有会话变体：negotiate（附带页）→ 暂存页与元素（不传 blob）→ 错误 If-Match 得 412 → 同一会话以正确 If-Match 得 DPE_MISSING_CONTENT → 补传 blob → 同一会话提交得 200 updated。第二次是 400 而非 410、补传后 200，证明失败的 commit 未消费会话。

    判红面扩大：先判 blob、后判前置条件的服务端会被判红；合规服务端不受影响。检查总数变为 282（执行 281、skip 1），order 章 54 条；服务端 CI 的执行数基线请按新计数更新。该检查随 0.6 发布，不进 0.5.x。

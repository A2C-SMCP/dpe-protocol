# 官方 Git connector

把 Git 仓库的**提交历史**映射为 DPE 文档的 **dpe-run 插件**（[connector 契约](../../spec/connector-contract.md) §6）。
插件只产出源内容：不计算 hash、不接触 DPE remote 与 remote 凭证、不感知任何服务端实现的概念。

## 定位

DPE 不表达完整仓库，而是成为 **Git 仓库变更历史的可读面**：使用者（如检索增强的 LLM）用它
召回「什么时候、为什么改过」，再凭提交 SHA 调 Git 工具查看现状或复原历史。因此：

- 映射只读**提交元数据与提交说明**——不读树、不读 diff、不读文件内容；
- 改动摘要与 diff **不进 DPE**（那属于 Git 工具），提交说明是召回质量的全部来源；
- 文档的身份是仓库，页与元素是这条历史的时间切面（见下）。

本包是其第一个交付（[Issue #65](https://github.com/A2C-SMCP/dpe-protocol/issues/65) 的骨架 + [Issue #96](https://github.com/A2C-SMCP/dpe-protocol/issues/96) 的映射重构，
全量枚举）与 [Issue #66](https://github.com/A2C-SMCP/dpe-protocol/issues/66) 的增量游标与删除 / 移动意图；blob 是后续拆分（#67）。

## 用法

```bash
# 开发环境（path 源指向同仓的 sdk/python 成员包，见 pyproject.toml）
uv sync
uv run pytest
uv run dpe-git-connector        # 不直接交互使用：由 dpe-run 以 stdio 启动

# 实例定义（connector 契约 §4.4）：单仓库
{
  "definition_version": 1,
  "id": "docs-repo",
  "remote": { "url": "https://dpe.example.com/remotes/x" },
  "uri_prefix": "git://docs/",
  "plugin": { "manifest": "connectors/git/dpe-connector.json",
              "command": ["dpe-git-connector"] },
  "config": { "repo": "/srv/git/docs", "branches": ["dev"], "since": "…" }
}
```

### 配置

| 字段 | 必填 | 说明 |
| --- | --- | --- |
| `repo` | 与 `root` 二选一 | 单个仓库的**本地路径**（本连接器用本机 git 读取，不代为访问远端） |
| `root` | 与 `repo` 二选一 | 容纳多个仓库的目录：**递归发现**，每个仓库一篇文档 |
| `branches` | 否 | 跟踪的分支名集合；缺省只有默认分支（默认分支本身不产页，由月页表达） |
| `default_branch` | 否 | 默认分支名；缺省取仓库的 `refs/remotes/origin/HEAD`（由远端声明） |
| `since` | 否 | 历史起点提交（含起点，见下）；**仅 `repo` 模式**——一个提交 id 对多仓库没有意义 |

- **默认分支**：显式配置优先；否则取 `refs/remotes/origin/HEAD` 的符号目标。**不看本地 `HEAD`**
  ——工作区 checkout 会改动它，那是运行环境状态而非源内容，会让整篇文档的默认分支随环境漂移、
  制造伪变更。两者都拿不到时：`repo` 模式在 initialize 以 `invalid_config` 拒绝，`root` 模式下
  该仓库产出条目级错误（其余仓库照常枚举）。
- **分支名解析**：`refs/remotes/origin/<name>` 优先，其次本地 `refs/heads/<name>`；解析不到
  （未建、已删）不产该页、也不报错——与「删除分支 = 删页」一致。
- `root` 递归发现仓库（不进入已发现的仓库，子模块与嵌套仓库都不是独立仓库；不跟随符号链接），
  以**相对 `root` 的路径**作为身份；`root` 自身不能是仓库。仓库目录消失 / 改名会表现为
  `delete` / `move`（见「增量与删除 / 移动」）。
- `repo` 必须是仓库根目录（裸仓库则是裸仓库目录本身）；空仓库（无任何提交）合法：零页文档。

## 映射规则

> 本节的规则就是本连接器的内容定义。**规则变更 = 全部文档的内容变化**（增量同步会当作内容
> 变化重新投递与重学）——发布时必须在 release notes 里标注为「全量内容变化」。

### 文档 = 一个仓库

- `file_uri` = 实例 URI 前缀 + 仓库标识（`repo` 模式取目录名，`root` 模式取相对路径）。标识按
  原始路径字节经 RFC 3986 百分号编码表达（非 UTF-8 的路径字节同样可表达），再调
  `dpe_hash.normalize_file_uri` 规范化。前缀必须以 URI 分隔字符（`/` `?` `#`）结尾——码点前缀
  匹配不识别段边界，`git://docs` 这样的前缀拼上标识会改写 authority，initialize 时会被拒绝。
- `file_type` = `git_repo`（core §2.5 推荐登记表；提交历史与语言无关）。
- **不写 `title`**：title 是内容、会进 doc_hash；从目录名或路径推导会让仓库改名变成
  「move + 内容变化」，破坏 move 保留学习产物的语义。身份只放在 `file_uri` 里。
- `doc_metadata` 留空：没有满足「不可变源事实、且不必经 file_uri 表达」的键。

### 页：默认分支按月，其他分支各一页

- **默认分支按月一页**。月份 = 改动**进入主线的时间**：该提交由 first-parent 链上哪个提交
  引入（链上提交就是它自己，合并带入的提交是把它合并进来的那个提交），就取那个提交的
  committer 时间（UTC）的 `YYYY-MM`。**被合并进来的提交随其合并提交归月，不按自身提交
  时间**（分支上的提交时间可以早于或晚于合并时间，都与归月无关）。月份由提交时间得出，
  不是由位置算出的序号（core §2.4）。`page_metadata = {ref: <默认分支名>, period: "YYYY-MM"}`。
- **其他跟踪分支每条一页**：只含该分支独有的提交（`<default>..<branch>`，即不在默认分支
  历史中的提交）。`page_metadata = {ref: <分支名>}`。分支页可以为空（分支已合并、尚未删除
  时没有独有提交）——空页是合法内容，表达「这条分支存在且没有独有提交」。
- **页序**：月页按月份升序在前，分支页按分支名（UTF-8 字节序）在后；配置里含默认分支名
  不产生重复页。
- `since` 的粒度是**引入提交**：保留起点所在的那一批（含被合并带入的提交）与之后的全部提交。
  起点不在默认分支历史中时 initialize 即拒绝（配置错误，早失败早诊断）。`since` **只作用于
  默认分支的月页**——分支页只表达 `<default>..<branch>` 的独有提交，没有「引入提交」可言，
  不受起点过滤。

### 元素 = 一次提交

- `category` = `NarrativeText`；`text` = 提交说明全文（**原样**，不剥离、不改写，含结尾换行）。
- `metadata`（Git 中不可变，属源内容、全部进 hash）：
  `{commit: <SHA>, author: "Name <email>", authored_at: RFC 3339 UTC, committed_at: RFC 3339 UTC}`。
  `commit` 是调 Git 工具查现状 / 复原历史的钥匙，也使同文说明的不同提交互不混同；作者 ident
  原样（**不做 mailmap**——改写过的 ident 不是源内容）。
- **页内顺序**：旧在前（**自有拓扑序**——见「确定性」的自有排序规则，只依赖提交图，不依赖
  git 的输出次序）；被合并带入的提交排在其合并提交之前。
- 不写易变字段（抓取时间、当前 HEAD 状态等），不写由位置算出的序号。

### 增量友好性

- 新提交进入主线只改**当月页**（必要时新增一页）；已满月份页的 `page_hash` 不再变化。
- force-push 只影响改写涉及的月份页与分支页（月页边界由提交时间决定，不连锁）。
- 新建分支 = 新增一页（名字排在中间即「文档中间插入一页」）；删除分支 = 删页。

## 增量与删除 / 移动（契约 §6.4、§6.5、§6.8）

`capabilities.supports_cursor = true`。每轮结束批给出游标，下一轮据此只产出变化：

- **游标**记录上一轮各仓库的**状态指纹**与**移动键**，外加数据源摘要（实例前缀 + 配置）与
  当轮的远端单元素上限；不透明、自包含（`g1.` + base64url 的压缩 JSON）。解释不了（格式、
  版本、数据源不符）时回退全量轮并标 `incremental: false`，不报错。游标内的格式版本为 2
  （#170，前缀仍是 `g1.`）；升级前留下的 v1 游标只要上限没变照样解释（增量轮），上限也变了
  才回退一次全量轮。
- **远端上限变化仍是增量轮**（#170）：`remote_limits.max_payload_bytes` 与游标里记的不同时，
  同一状态下的产出可能不同（守卫结论变了），于是各仓库都**不按指纹跳过**、逐个重新产出；
  仓库集合的判定照旧——期间被删或改名的仓库仍产出 `delete` / `move`，`incremental: true`。
  这一轮里没能在新上限下产出的仓库（如守卫转出的 `content_invalid`）沿用旧记录，新游标的上限
  也退回旧值，下一轮仍按新上限重扫——新游标不越过未产出的变更（§6.8）。
- **状态指纹** = 默认分支名与 tip、`since` 解析出的提交、各跟踪分支的 tip。映射只依赖这组
  值（提交按 SHA 不可变），所以指纹不变即文档不变：增量轮直接**跳过**该仓库，不读提交日志。
  指纹与映射用同一次解析出的 tip，两者之间仓库被推送也不会记下与内容不符的指纹。
- **增量粒度是仓库**：一次 DPE commit 是整篇文档，有变化的仓库仍产出整篇文档；页级复用由
  运行器的 tree hash 承担（未变的页在 remote 上已存在）。
- **删除**：上一轮有、本轮在 `root` 下发现不到的仓库 → `delete`（`repo` 模式只有一个仓库，
  不产意图）。
- **移动**：消失的仓库与本轮新出现的仓库**根提交集合与默认分支名都相同、且一一对应**
  → `move`（#96）；`move` 之后总在新 URI 上紧跟产出 `document`，内容未变时运行器判为
  `unchanged`、不发写（connector §6.5）。万一源已在早先一个未推进游标的轮里被本实例删除，运行器
  据此把目标建出来，而不是让 move 永久失败；move 因目标被占用等原因未达成时，运行器不会用这条
  document 覆盖目标（§7.2「move 未达成之后的目标 document」，#178）。代价是每次改名都要完整映射
  一次目标仓库（读树、生成文档），不再凭指纹跳过。同键多对多
  （如同一仓库的多份克隆同时改名）无法确定配对，按 `delete` + 新建处理；空仓库没有根提交，
  不参与配对。
- **发现不完整时不产出 delete / move**：存在读不了的子树，或某个新出现的仓库算不出移动键。
  被藏起来或算不出键的仓库可能正是移动目标——先删了源，下一轮的 `move` 会永久失败。此时
  消失仓库的记录原样带入新游标，移动键与某个消失仓库相同的新仓库先以条目级 `error` 上报；
  这样的轮必有 `error` 条目，运行器不推进游标（§6.8），子树恢复后下一轮重判。
- **新游标不越过未产出的变更**：仓库映射失败、超限或分段中途放弃时，保留它上一轮的记录
  （没有就不记）。
- 游标随仓库数增长：结束批放不下时单独多发一批（空 `items` + 游标）；游标本身超过单条消息
  上限时本轮回 `cursor: null`（不提供游标），记 warning。

### 大文档的分段与守卫

- 单条响应不超过 `max_message_bytes`；一篇文档装不下时按 §6.5 在**页边界**分段（首段带
  `document`，续段只带 `file_uri` 与页，同 `file_uri` 的各段连续出现，非末段 `continued: true`）。
- **单页自身**装不进单条预算时整篇文档以条目级 `error`（`content_invalid`）如实上报
  （§6.5：MUST NOT 发送超限消息）。续批之间单条预算可能随请求 `id` 变长而缩水（响应必须
  回显 id）：在途分段文档的下一页在批首也装不下时，该文档整篇失败（条目级 `content_invalid`，
  已发出的分段未闭合），本轮其余条目照常推进。
- `max_message_bytes` 过小或请求 `id` 过长，使单条预算连最小的 `error` 条目都装不下时：
  `scan` 以 JSON-RPC error（`-32602`）应答，本轮失败（运行器按 §6.4 中止本轮、退避重试）。
  错误响应的整行也按上限校验（含握手失败的应答）：装不下消息正文时只保留错误码（`id` 必须
  回显）——任何路径都不发超限消息。唯一例外是上限尚未解析出的极早期应答（§6.2 的三条固定
  形状解析错误）：`max_message_bytes` 小于它们的字节数（约 100）时实例本就不可用。
- 单个提交的说明超过固定预算（`ELEMENT_BUDGET_BYTES`，1 MiB，按元素对象 JCS 字节计）时按行
  边界切成多个连续元素（类别与 metadata 复制到每个片段）；预算**不读** `remote_limits`——
  同一份源在任何远端都得到相同的 hash。`remote_limits.max_payload_bytes` 只作**守卫**：
  切分后元素仍超限的让该文档产出 `error`，如实上报，不静默按远端值重新切分。

### 确定性

同一仓库状态上的两次全量枚举产出相同的条目序列与相同的 `doc_hash`（契约 §8.3 判据 1）。
保证来自：提交按 SHA 引用（枚举期间不随引用漂移）、**元素序由本连接器自己规定**（见下，
与 git 的输出次序无关）、时间统一归一为 RFC 3339 UTC、固定切分预算。`markdown` 等文件
格式不参与映射，不再有解析器版本这类内容影响因素。

**自有排序规则**（页内元素序是 `page_hash` 的一部分，必须只是提交图的函数）：

- 从起始提交（默认分支 tip / 分支 tip）出发做**后序深度优先遍历**：先按**父提交的记录
  顺序**（第一个父、第二个父……；记录顺序本身是源内容）递归访问每个父提交，最后输出该
  提交自身；每个提交只输出一次；
- 该顺序保证父提交先于子提交（旧在前）、被合并带入的提交排在其合并提交之前；平局完全由
  图与父记录顺序决定——**没有**任何按时间或 SHA 的隐含序，因此**跨 git 版本稳定**（git 的
  `--topo-order` 等排序只用来取集合，不参与内容——升级 git 不改 hash）；
- `<default>..<branch>` 的独有提交对集合做同一遍历（从分支 tip 出发；不在集合里的提交
  被跳过且不下探——被排除提交的祖先也必被排除）；
- 月划分与 `since` 切割在同一次遍历的结果上按「引入提交」进行（见上）。

## 本包不做的事（后续拆分）

- 不产 `blob`：提交历史本身不含二进制（#67 按本映射重新评估是否仍需要）；
- 不接触 DPE remote、凭证与 hash（hash 由运行器计算，契约 §6.6）。

## 已知限制

- **召回质量取决于提交说明质量**：`text` 就是说明原文；「fix」「wip」这类说明基本召回不到。
  这不是映射的缺陷，而是「源即内容」（plan §0.1 P2）的如实体现。
- **同一提交可能出现在多个页**：分支页只放 `<default>..<branch>` 的独有提交，但两条都未合并
  的分支共享提交时，该提交会在两个分支页各出现一次。去重的单位是行，不是 hash（见 #96）。
- **仓库不可用按条目级错误处理**：`root` 模式下单个仓库损坏（含默认分支无法确定）只影响
  该文档，本轮继续；`repo` 模式在 initialize 即拒绝（配置问题早暴露）。默认分支无法确定标
  `retryable: true`：仓库可能正在克隆 / 初始化（`origin/HEAD` 尚未写入），重跑可能成功。
  `root` 下**子孙目录读不了**（权限等）同样只影响该子树（路径即身份，条目级
  `source_unavailable`）；`root` 自身读不了则没有可枚举的范围，整轮失败（`-32003`，退避重试）。
- **内容类失败不可重试**：提交说明或作者 ident 不是合法 UTF-8（历史里真实存在，需绕过
  `git commit` 写入）、时间戳不合规——这些内容进不了合法 DPE 值，条目级归属是
  `content_invalid`、`retryable: false`；读取类失败（仓库不可读、默认分支解析不到）才是可
  重试的 `source_unavailable`（§6.5 的封闭枚举按定义区分）。不做替换或猜测编码。
- **每个仓库每轮多次调用 git**：有变化的仓库要做默认分支解析、first-parent 链、提交日志、
  每条分支一次日志，成本随提交数与分支数增长；超大仓库的读取加速留给后续拆分。**无变化的
  仓库**每轮仍要解析状态（若干次 `rev-parse` / `symbolic-ref`，不读提交日志），成本随仓库数
  与跟踪分支数线性增长。单批里跳过的仓库数有上限（到上限即以空批 + `next` 结束本批），单个
  `scan` 请求的工作量因此有界；但有仓库消失的轮里，轮首要为全部新出现的仓库计算移动键，这部分
  在第一个 `scan` 里一次做完。
- **一个新仓库读不了就扣住整个实例的删除与改名**：发现不完整（某个新出现的仓库算不出移动键，
  如新 `git init` 的仓库没有 `origin/HEAD` 也没配 `default_branch`）时，本轮全部 delete / move
  都推迟（见「增量与删除 / 移动」）。这是 fail-closed 的代价：修好那个仓库（或配置
  `default_branch`）之前，其他仓库的删除与改名不会写到 remote。
- **游标解压有上限**：`max(1 MiB, 16 × 压缩长度)`，防止被篡改的游标撑爆内存。上万个同源克隆
  使游标压缩比超过 16 时，插件会解不开自己给出的游标而每轮回退全量（日志有 warning）。
- **映射不受本机配置影响**：`git log` 固定 UTF-8 输出、不显示签名；不应用 `refs/replace` 与
  grafts。浅克隆的边界计入仓库状态（`fetch --deepen` 后会重新产出）。system / global 配置
  不读取；命令行级配置（`GIT_CONFIG_COUNT` 系列）保留，部署方可经实例定义的 `plugin.env`
  注入，例如仓库与运行器属主不同时放行 `safe.directory`。
- **需要 git ≥ 2.32**：`GIT_CONFIG_GLOBAL`（隔离全局配置）自 2.32 起生效，`--end-of-options`
  更早可用。`initialize` 时检查：版本更低或无法确定时以 `-32005`（invalid_config）拒绝，
  git 起不来（不存在、不可执行、`git --version` 10 秒内未完成或退出码非零）同样拒绝；运行器
  按实例级失败报告（退出码 3，不自动重试），消息带实测版本与下限或失败原因。偶发的启动失败
  修好环境后重跑即可。
- **浅克隆 / 嫁接仓库**：git 把浅边界的提交表现为**无父**（cauterize），枚举自然止步于边界
  ——只表达克隆可见的历史，不报错（有防退化测试钉住）。
- **单篇文档的全量历史驻留内存**：一个仓库一篇文档意味着枚举时要把它的全部提交（含说明）
  读进内存再分页；内存随该仓库的提交数线性增长。这是「一个仓库一篇文档」的固有代价，推送
  规模由运行器的逐层协商承担（#68 验收）。
- **请求的上界与 `cancel` 的定位**（依据 §6.1）：本插件每个请求都有产出的上界（批次条目数
  `max_items`，缺省上限 1000；编码字节数 ≤ 单条预算）。`cancel` 只记录最近一次被取消的请求
  id，对重复到达的同 id 请求如实回 `-32001`，不改动在途状态。注意留一条前提：**输入侧没有
  字节上界**——一次 `scan` 的耗时随仓库规模增长；将来若某个请求可能明显变长，必须把读循环
  改成能并发处理控制消息的结构（select / 线程）。

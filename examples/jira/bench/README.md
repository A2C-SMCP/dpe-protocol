# Jira 映射粒度基准测试（#237）

对比 Jira 示例插件的两种文档粒度：

- **工单 = 文档**：正式插件（`dpe_jira.server.Serve`），每个工单一篇，另有每个项目一篇项目文档；
- **项目 = 文档**：`project_mode.py`，**只用于本基准测试**，不进插件的正式映射，也不是配置开关。
  每个项目一篇，项目三页之后每个工单依次占正文、评论、字段、附件页；任一工单有变化就重新拉取
  整个项目来组装整篇（插件跨轮只有游标，这是这种粒度的真实成本，不做绕过）。

两种模式除粒度外完全一致：同一个运行器（真实 `dpe-run`）、同一个参考服务端、同一份合成数据、
同样的 ADF / 字段 / 附件规则与单条消息预算。

## 用法

```bash
cd examples/jira
uv sync
uv run python -m bench run --tiers 200,2000 --out /tmp/bench          # W1–W12，两种模式
uv run python -m bench run --tiers 20000 --out /tmp/bench-20k         # 大档单独跑（数十分钟）
uv run python -m bench run --tiers none --scale 1000,5000,20000 --out /tmp/bench-w13   # 只跑 W13
uv run python -m bench run --tiers 200 --workloads W3,W10 --out /tmp/bench-quick      # 部分工作负载
```

产出 `results.json`（全部指标）与 `report.md`（每个工作负载一张两列对比表）。冒烟用例在
`tests/test_bench.py`，随 `uv run pytest` 运行（几十个工单，不测性能）。

## 数据

- **合成数据**（`synth.py`）：按 `profiles/profile-a.json` 的分布生成，200 / 2,000 / 20,000 个工单
  分布在 1 / 5 / 20 个项目中。每个工单用独立的随机源（种子 + 工单 id），同一参数得到逐字节相同的
  数据；附件字节按需生成，不常驻内存；
- **profile**（`profile.py`）：对真实 Jira **只读**采样得到的脱敏分布——各量的分位数、比例与
  非空率，经插件自己的映射转成元素后统计。不含任何原文、key、项目名、人名、取值名称与工单总数；
  采样范围只在命令行给出，不写进输出；
- **真实校准**：`python -m bench real …` 对真实 Jira 只读地跑两种模式的首轮全量与无变化轮，remote
  是本机参考服务端（内容不离开本机）。结果只含数字（失败条目不带 URI），**只留在本机、不提交**——
  规模属于内部信息。凭证经实例定义的 `file` 来源引用，不进命令行与输出；跑完删除输出目录，
  不再需要时撤销 token（守则同 #223）。

## 工作负载

| # | 场景 |
| --- | --- |
| W1 | 首轮全量 |
| W2 | 无变化轮 |
| W3 | 1 个工单加 1 条评论 |
| W4 | 批量改 50 个工单的状态 |
| W5 | 同一批 20 个工单连续 10 轮、每轮都改状态（累计） |
| W6 | 热点工单：先加到 2,000 条评论（准备轮另记），再追加 1 条 |
| W7 | 新建 1 个、删除 1 个工单 |
| W8 | 1 个工单换项目（只有 1 个项目的档跳过） |
| W9a | 10 个工单变化，其中 1 个在枚举后读到 404（条目级失败） |
| W9b | 10 个工单变化，其中 1 个读取返回 5xx（本轮中止） |
| W10 | 模拟 Jira 按每秒 10 个请求限流（429 + `Retry-After: 1`），跑 W3 |
| W11 | 写入生效、确认前 kill -9 运行器（#213），源回到原状后重跑 |
| W12 | 他人带 CAS 改写 remote 上 1 个工单所在的文档，源随后也改，`report` 策略 |
| W12-after | W12 之后，被改写的工单与同项目另一个工单再变 |
| W13 | 仅项目模式：单个项目逐档放大，直到首轮失败 |

同一模式的 W1–W12 在同一个实例上**顺序**执行（免得每项都重做首轮全量）：每项从上一项结束时的
收敛状态出发；W9a、W9b 之后（以及 W10 若失败）跑一轮不计分的恢复轮，W11 的计分轮本身就是恢复；
W12 的冲突不会自愈，排在最后，之后源再变一次、再跑一轮（W12-after），实测冲突之后的变化能否推上去。两种模式自始至终
用 `conflict_policy.commit = report`（中途改策略会被运行器当作配置变化而改跑全量轮）。

## 指标口径

| 指标 | 采集 |
| --- | --- |
| 耗时 | 运行器子进程的墙钟（快照等采集不计入） |
| DPE 请求数、写请求数、请求体字节 | 记录代理（请求体按解压后计） |
| Jira 请求数、响应字节、429 次数 | 模拟 Jira 的计数差（真实校准时没有） |
| doc_hash 变化的文档数 | 前后两轮 remote 快照对比（新增、删除、变化之和） |
| 新出现的 page_hash / content_hash 数 | 同上，本轮之后 remote 上出现、之前没有的对象（重学范围的代理指标） |
| 失败波及的工单数 | 报告里失败条目所在文档承载的工单数（工单模式 1，项目模式为整个项目） |
| 插件 RSS 峰值 | `rsswrap.py` 包装插件进程，取子进程的 `ru_maxrss` |
| 游标字节数 | 运行器 `state.json` 里的游标长度 |
| 变更可见延迟 | 本轮开始到该文档最后一个写请求完成（W3、W4） |
| 服务端文档数、对象数 | remote 前缀内的文档数，以及去重后的 page / content 对象数 |

限额：参考服务端缺省（单请求体 8 MiB），运行器缺省单条消息上限（32 MiB）。

## 文件

| `report.py` | `results.json` → Markdown 对比表 |
| `rsswrap.py` | 插件内存峰值包装 |
